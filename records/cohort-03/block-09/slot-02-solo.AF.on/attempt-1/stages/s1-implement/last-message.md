I've built the job tracker: an HTTP server, a separate worker process, and a browser page, all sharing one SQLite database. The build passes, both processes start with the existing commands, and the smoke checks (2/2) and contract checks (5/5) pass. I also tested by hand that bad requests are rejected, that a job with `failAttempts: 3` ends `failed` after 3 attempts, and that the worker recovers after being killed with `SIGKILL`.

**What changed**
- **`src/db.ts`**: opens the database at `DATABASE_PATH`, creates the folder if it's missing, and sets up two tables: one for jobs and one holding the worker's last heartbeat. Both processes use it, plus a shared function that turns a database row into the job JSON shape.
- **`src/server.ts`**: all the routes from the task, including `404 not_found` for unknown paths and `405 method_not_allowed` for wrong methods. Validation lists every bad field in one response. Idempotency keys are unique in the database and compared against the payload after defaults are filled in, so a key can never create a second job, even after a restart. `/health` reports the worker as up if its heartbeat is less than 3 seconds old. The server shuts down cleanly on `SIGTERM`.
- **`src/worker.ts`**: writes a heartbeat every 500 ms and checks for queued jobs every 100 ms, taking the oldest first. Each step takes 100 ms and saves progress as it goes. A failed attempt is retried after 500 ms, and the job is marked `failed` with `"transient failure"` after the third attempt. On `SIGTERM` it puts any half-done job back in the queue before exiting.
- **`ui/index.html`**: the form, the error region and the job list, with all the required `data-testid`s. Number fields are sent as numbers, the error region names each rejected field, and the list refreshes every 0.7 seconds. Each job's input text uses its own testid, `job-input-text`, so it doesn't clash with the form's `job-input`.

**Decision for you:** when the worker restarts, any job that was `running` goes back to the queue and its interrupted attempt isn't counted. That keeps jobs within the 3-attempt limit and gives the same outcomes for `failAttempts` as an uninterrupted run. The catch is that `attempts` then leaves out an attempt that did start. If you'd rather count it, it's a one-line change, but a job could then reach 4 attempts.

The worker assumes it is the only worker running. Nothing is committed; the changes are saved in the working tree.
