# Review findings

1. [minor] src/jobs.ts:148-155 — Recovery undoes the interrupted attempt by running `attempts = attempts - 1`. The task defines `attempts` as "the number of processing attempts started so far", so an attempt that started and was then cut short by SIGKILL or SIGTERM drops out of the count. For example, a `failAttempts: 0` job killed mid-run and then finished reports `attempts: 1`, but two attempts were started. A check that counts attempts across a restart would see a number that is too low. Separately, a worker that keeps crashing on the same job re-runs that attempt forever without using up its budget.
   Evidence: `recoverInterruptedJobs` runs at worker startup (worker.ts:31) and again on graceful shutdown (worker.ts:74), and both times it decrements `attempts` for every `running` row. The comment says this was done on purpose, to stay within the 3-attempt budget.
   Fix: Stop decrementing `attempts`. Set the job back to `queued` with `completed = 0`. In the same UPDATE, handle a job that has already started its third attempt (`attempts >= 3`): if that attempt was due to fail (`attempts <= fail_attempts`), mark it `failed` with `error = 'transient failure'`. Otherwise let it re-run once more without incrementing `attempts` (for example, skip the `attempts + 1` in `claimNextJob` when a recovery flag column is set). This keeps `attempts` accurate and capped at 3, and still processes the job again.
